### MUプラグイン配置の注意

MUプラグインは**配置された次のWordPressリクエストから自動で読み込まれます**。有効化ボタンやactivation hookを安全な待機段階として使えず、管理画面の通常の「無効化」では止められません。

- アップロード先は公開ディレクトリ外の同一ファイルシステム上で準備し、本番と同じPHPで`php -l`を実施します。1ファイルずつrenameで置換し、各段階で読み取り確認を行います。6ファイルを一括展開しません。
- `*.backup.php`や`*.pending.php`もMU直下では実行対象になるため置きません。バックアップは公開ディレクトリ外へ保存します。
- `ojl-series-preview.php`はRESTルートだけでなくプレビューリンクのフィルターも登録します。配置直後に編集画面の導線が切り替わるため、段階3のReact確認前に配置しません。
- WordPress管理画面に入れなくてもSSH/SFTPで置換を戻せることを必須とします。OPcacheの更新・既存キャッシュの再検証方法も確認します。
- CPT登録のためのDB移行・記事一括更新は行いません。rewriteは必要時に一度soft flushし、`.htaccess`全体の上書きや毎リクエストのflushは行いません。

### Webhook・GitHub Actionsの誤起動防止

停止・再開は新しい仕組みを追加せず、既存の2つのスイッチを使います。WordPress定数を変更するときは既存定義を変更し、重複定義しません。Actions Variablesはrepository／production environmentの設定元と優先関係を確認し、ジョブで評価される有効値がfalseになったことを確認します。

| 状態                                       | WordPress `OJL_FRONTEND_DEPLOY_ENABLED` | Actions `PRODUCTION_DEPLOY_ENABLED`         |
| ------------------------------------------ | --------------------------------------- | ------------------------------------------- |
| CMS配置・下書き確認・Reactステージング確認 | `false`                                 | `false`                                     |
| main反映後の手動dry-run                    | `false`                                 | `false`（dry-runのみ実行可能）              |
| 意図した初回の本番同期                     | `false`                                 | `true`（他のpush・手動実行を止めて1回実行） |
| 正常確認後の通常運用                       | 記録した元の状態                        | 記録した元の状態                            |

Actionsのスイッチがfalseでもworkflow自体の記録は作られ得ます。本番同期がスキップされていることまで確認します。スイッチ変更は開始済みのジョブを止めず、同時実行制御も通知を永続的にまとめる仕組みではありません。`wordpress_content_changed`の手動送信や失敗ジョブの安易な再実行は行いません。main更新直後のpush起点ジョブがスキップ済みであることを確認してから、段階6の通常実行を開始します。

既存の全件再ビルド、同一リクエストの通知集約、30秒の重複抑止、デプロイの直列実行を維持します。差分ビルド・新しい通知基盤・新Secretsは不要です。Shopifyジョブ・コマンド・別CMS改修は専用候補に含めず、実施当日の最新mainにも追加されていないことを再確認します。元から稼働する別処理が見つかれば、その影響を確認するまでリリースを止めます。

## 残るリスクと対処

- 本番固有のPHP・DB・プラグインの組合せを事前に完全再現できません。バックアップと段階ごとの正常性確認、SSH/SFTPによる即時復旧を必須とします。
- MUプラグインのFatal errorは通常記事API・管理画面にも影響し得ます。静的な公開記事が表示されても正常と判断せず、既存CMS APIも確認します。
- 公開記事ゼロでも公開した連載本体は紹介ページの生成対象です。準備中の連載と確認用記事は下書きを維持します。
- Webhookを止めている間の変更は自動再送されません。編集・予定公開を避け、初回全件ビルドの対象時点を記録します。停止中に変更があった場合は記録し、最新データで全件再生成してから再開します。
- 既存同期は非原子的です。同期中と60秒のHTMLキャッシュ期間には旧HTMLと新アセットが混在し得ます。公開の少ない時間に反映し、必要なら前回のハッシュ付きアセットを候補へ保持します。リリース切り替え基盤の改修はしません。
- 予約公開の実時刻、XServerのAPI制限、CORS、実機Safariは本番接続での確認が残ります。初回の正式公開を監視し、未確認を解消するまでは時刻保証済みとして運用しません。

## バックアップ

バックアップは公開ディレクトリ外の権限を制限した保管先へ取得し、認証情報やDBダンプをGit・公開成果物へ入れません。XServerの自動バックアップの対象・取得時刻・復旧方法も併せて確認します。

**取得だけでなく復元確認を着手条件にします。** DBダンプの整合性・取得時点を確認し、既存ローカルの隔離MySQL等、本番と互換性のある非公開の復元先で読み戻せることを確認します。データの持ち出し条件を守り、外部連携は停止します。SQLiteでの機能テスト成功だけではMySQLバックアップの復元確認に代えません。ファイルもバックアップから復旧用一時領域へ取り出し、ハッシュと不存在一覧を確認します。独立したWordPressステージングの新設は不要です。

| 対象         | 保存内容                                                                                                                                                      |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WordPress    | DB全体の整合したダンプ、実際に稼働中の上記6ファイル（未設置なら不存在も記録）、関連するPHP実行環境・有効プラグイン・rewrite設定、設定ファイルの保護された退避 |
| DBの重点項目 | posts、postmeta、options。連載メタだけでなく既存URLライフサイクルの履歴も含める                                                                               |
| フロント     | 現在配信中のルートファイル一覧と内容、`.htaccess`全体、管理する8ディレクトリ、ハッシュ一覧。連載2ディレクトリが未設置なら不存在を記録                         |
| 運用設定     | WebhookとActionsの元の有効状態、直前の成功ビルド／コミット、実際の同期先とマーカー。トークン値を作業記録へ転載しない                                          |

フロントのバックアップはGitの旧コードだけでは不十分です。当時のWordPressデータで生成されたHTML・JSONとハッシュ付きアセットを一緒に保存してください。今のDBから旧コードを再ビルドしても、配信直前の状態には戻りません。

## ロールバック

### CMS配置途中に問題が起きた場合

段階2・4・5で障害が起きた場合は本番フロント未変更のため、フロント復旧を待たず、その段階のCMSファイルをSSH/SFTPで直ちに戻します。Fatal errorの場合は原因となったMUファイルを先に実行対象外へ移動します。管理画面の無効化操作には依存しません。WebhookとActionsは停止状態を維持します。

- 段階2：`ojl-series.php`と`editor.js`を直前の組合せへ戻します。
- 段階4：新プレビューのMUファイルを実行対象外へ移し、旧プレビューUI・エンドポイントを退避版へ戻します。新プレビューが依存するコアは、当該MUファイルを外す前に撤去しません。
- 段階5：Webhookの異常なら当該ファイルを先に戻します。保存の異常は編集を停止し、関連するコア・プレビューを整合した組合せへ戻します。DBを書き換えての修復や全体リストアを即断しません。

戻した後は公開サイトだけでなく既存記事API・管理画面・プレビュー・エラーログを確認します。解決するまで次段階へ進まず、必要に応じて安全な旧版で編集を再開します。

### フロントだけに問題がある場合

1. 次のデプロイとWebhookを停止し、同期が進行中でないことを確認します。元の状態を記録します。
2. 直前の配信物を復旧候補として一時領域へ展開します。反映で新設した連載ディレクトリがバックアップにない場合、復旧候補側では空にして新ファイルの削除対象を明示します。
3. 既存の保護・`.htaccess`結合処理を維持して管理ディレクトリと既存ルートファイルだけを戻します。`/lp/`やCMS、未知のディレクトリへ削除同期しません。
4. 今回新設し、バックアップには存在しなかった`series-index.json`は個別に除去します。既存のルート同期はルートファイルを削除しないため、この確認が必要です。今回だけ追加した他のルートファイルがあれば同じ一覧に従います。
5. `.htaccess`は退避したOJL管理ブロックへ戻し、現在のXServer設定・認証などマーカー外は保持します。設定破損が原因で全体復元する場合も、反映後に他の管理者が追加した設定を失わないよう比較します。
6. キャッシュの再検証または既存手順のパージ後、通常記事・トップ・404・`/lp/`を確認します。ステージングの新プレビューとCMSは互換性がある限り維持できます。連載のDBデータは削除しません。

### CMSも戻す必要がある場合

本番フロント反映後にCMSも戻す場合は、編集・自動実行を停止し、フロントとCMSの互換性を確保して退避版へ戻します。CMSにFatal errorがある場合は、そのファイルの隔離を先に実施します。新プレビューを外してから旧プレビューUI・エンドポイントを戻し、最後に必要なコアを戻します。Phase 1が以前から稼働していた場合は、その版を維持します。不存在だったファイルだけを取り除き、旧`series_contents`には触れません。必要な場合のみWordPressのrewriteをsoft flushします。OPcache等の既存キャッシュ更新手順も実施します。

通常のコード復旧ではDB全体を巻き戻しません。連載用postとメタを残しても、旧フロントの通常記事表示には影響しません。DB復旧が必要な障害の場合だけ、編集停止・バックアップ時点・その後の記事や他プラグインの更新を確認し、復旧対象と失われる差分を特定して合意した時点へ復旧します。投稿編集を止めただけでDB全体の更新が止まるとは判断しません。他の編集結果を上書きする全DBリストアを自動実行しません。

復旧後の旧コードをmainにも整合させるまでは、Webhook／Actionsを再開しません。GitHubから再実行するだけでは、現在のmainから問題の版を再デプロイする可能性があります。

## 停止条件

独立したWordPressステージングの不足は停止理由にしません。バックアップの取得・復元確認、SSH/SFTPでの復旧経路、自動実行停止の確認、PHP・InnoDB要件、Reactステージングの配置先・検索除外が満たせない場合は、本番配置を開始しません。開始後は各段階の確認表に従って停止・復旧します。

本番固有の組合せとCronを事前に完全確認できないリスクは残ります。初回の正式公開・予約公開を監視し、機能配置と運用確認の完了を区別して記録します。今回確定するのは手順だけです。バックアップ取得・設定変更・MU配置・Reactステージング更新・push・本番デプロイ・Actions起動は全て未実施で、別途の実施指示まで行いません。
